# Robot UI System - Project Background

## 1. このドキュメントの目的

このドキュメントは、本プロジェクトに関わるAIエージェントに対して、ロボット全体のソフトウェア構成、UIシステムの設計思想、および現在までに決定された前提条件を説明するためのものである。

これは個別機能の詳細な実装仕様書ではない。

AIエージェントは、個別のタスクを実装する前に必ずこの背景を理解すること。

実装仕様書、既存コード、およびこのドキュメントの間に矛盾がある場合は、以下の優先順位で判断する。

1. ユーザーからの最新の明示的な指示
2. 個別タスクの実装仕様書
3. 既存コードの実際の動作
4. このプロジェクト背景

---

# 2. プロジェクト概要

このプロジェクトは、手のひらサイズの小型自律ロボットを開発するプロジェクトである。

ロボットは、一般的なPCやスマートフォンのように大きなディスプレイ、キーボード、マウス、タッチパネルを持たない。

ユーザーインターフェースは非常に限定されている。

- 小型フルカラーOLEDディスプレイ
- 2つのタクトスイッチ
- ブザー

それにもかかわらず、ロボット自身が自律的に動作し、ユーザーがロボット上で複数の機能やアプリケーションを操作できる必要がある。

そのため、UIを単なる画面描画機能として扱うのではなく、ロボット上の複数アプリケーションが共有する、専用のUIリソースとして設計する。

---

# 3. 基本的なシステム構成

システムは大きく以下の3層に分かれる。

```text
┌──────────────────────────────────────────┐
│             Robot Applications           │
│                                          │
│  Default UI                              │
│  Robot Control                           │
│  Diagnostics                             │
│  Motor Test                               │
│  Future Applications                      │
└───────────────────┬──────────────────────┘
                    │
                    │ Unix Domain Socket
                    │ MessagePack
                    ▼
┌──────────────────────────────────────────┐
│               ui_server                  │
│                                          │
│  OLED Display                            │
│  L/R Buttons                             │
│  PWM Buzzer                              │
│                                          │
│  Priority-based UI ownership              │
└───────────────────┬──────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────────┐
│              Physical Hardware           │
│                                          │
│  SSD1331 OLED                            │
│  GPIO19 / GPIO26 Buttons                 │
│  GPIO14 Hardware PWM Buzzer              │
└──────────────────────────────────────────┘
```

アプリケーションはハードウェアを直接操作しない。

OLED、ボタン、ブザーを利用する場合は、必ず `ui_server` を経由する。

---

# 4. UIサーバーの役割

`ui_server` は、物理UIハードウェアの所有者である。

管理対象：

- SSD1331 OLED
- Lボタン
- Rボタン
- PWMブザー

UIサーバーは常時起動する。

アプリケーションはSocketを通じてUIサーバーへ接続する。

通信にはMessagePackを使用する。

---

# 5. UIの所有権

複数のアプリケーションが存在する場合、すべてのアプリケーションが同時にディスプレイやボタンを操作すると競合する。

そのため、UIサーバーは常に1つのクライアントだけにUIの所有権を与える。

```text
             ┌─────────────┐
             │ ui_server   │
             └──────┬──────┘
                    │
                    │ UI owner
                    ▼
             ┌─────────────┐
             │ One client  │
             └─────────────┘
```

UIの所有権は優先度によって決定される。

優先度の数値が小さいほど優先度が高い。

```text
0      最優先
10     高優先度
20     通常アプリ
100    Default UI
```

---

# 6. Default UIの位置付け

Default UIは、ロボットの通常時に動作する基本アプリケーションである。

ロボットが特定の機能を実行していない場合、Default UIがユーザーインターフェースを所有する。

Default UIは、いわばロボットの「ホーム画面」または「シェル」に相当する。

通常時：

```text
┌─────────────────────────────┐
│        Default UI           │
│       priority=100          │
└──────────────┬──────────────┘
               │
               ▼
          ui_server
```

他のアプリケーションが起動すると：

```text
┌─────────────────────────────┐
│        Other App            │
│       priority=10           │
└──────────────┬──────────────┘
               │
               ▼
          ui_server

Default UI ← PREEMPTED
```

他のアプリケーションが終了すると：

```text
Other App
    │
    ▼
終了

    │
    ▼

Default UIが再接続

    │
    ▼

UI ownershipを再取得
```

---

# 7. PREEMPTEDはエラーではない

Default UIが他のアプリケーションによってUIを奪われることは、正常な動作である。

ui_serverから：

```text
PREEMPTED
```

を受信した場合、Default UIはクラッシュしてはならない。

これは次の状態遷移を意味する。

```text
ACTIVE
  │
  │ PREEMPTED
  ▼
SUSPENDED
  │
  │ UI available
  ▼
RECONNECTING
  │
  ▼
ACTIVE
```

したがって、`PREEMPTED` は例外的な異常ではなく、アプリケーションライフサイクルの一部として扱う。

---

# 8. Default UIの責務

Default UIは以下を担当する。

## システム情報

- バッテリー電圧
- CPU温度
- CPU周波数
- Wi-FiのIPアドレス

## アプリケーション管理

- 利用可能なアプリケーション一覧の表示
- アプリケーションの起動
- アプリケーション終了後のUI復帰

## システム操作

- 再起動
- シャットダウン

## バッテリー警告

- 低電圧検出
- 画面警告
- ブザー警告

# 9. UIの制約

ディスプレイは96×64ピクセルしかない。

このため、UI設計では情報量を慎重に制限する必要がある。

PC向けのような複雑なGUIを作るべきではない。

UIは以下を優先する。

1. 現在の状態が一目で分かる
2. 操作方法が単純
3. 画面遷移が少ない
4. 文字が読める
5. 2つのボタンだけで操作できる

---

# 10. ボタン操作の哲学

ボタンは2つしかない。

操作体系は極力単純にする。

基本操作：

```text
L = 次へ
R = 決定
```

Lは循環する。

```text
A → B → C → A
```

Rは現在選択されている項目を決定する。

長押しは現在使用しない。

将来的に必要になった場合は、後から追加する。

---

# 11. Default UIの画面設計

メイン画面には、システム状態とメニューを同時に表示する。

IPアドレスは常時表示する。

バッテリー電圧、CPU温度、CPU周波数は一定間隔で切り替えて表示する。

例：

```text
IP: 192.168.1.10

BAT: 7.42V

> Applications
  System
```

一定時間後：

```text
IP: 192.168.1.10

CPU: 48.7C

> Applications
  System
```

さらに一定時間後：

```text
IP: 192.168.1.10

FREQ: 1500MHz

> Applications
  System
```

この方式により、96×64という小さな画面でも複数の重要情報を表示できる。

# 12. アプリケーションの追加

今後どのようなアプリケーションが追加されるかは、現時点では決まっていない。

したがって、Default UIのPythonコードを変更せずにアプリケーションを追加できる必要がある。

アプリケーション一覧はYAMLで管理する。

設定ファイル：

```text
/etc/robot-ui/applications.yaml
```

例：

```yaml
applications:
  - name: Maze
    command:
      - python3
      - /opt/robot/apps/maze.py
    priority: 10

  - name: Motor Test
    command:
      - python3
      - /opt/robot/apps/motor_test.py
    priority: 20
```

この設計により、アプリケーション追加は基本的に設定ファイルの変更だけで行える。

# 13. アプリケーションのライフサイクル

Default UIからアプリケーションを起動する。

```text
┌──────────────┐
│ Default UI   │
└──────┬───────┘
       │
       │ User selects app
       ▼
┌──────────────┐
│ Start App    │
└──────┬───────┘
       │
       ▼
┌──────────────┐
│ Other App    │
│ priority=10  │
└──────┬───────┘
       │
       │ UI ownership
       ▼
   ui_server
```

Default UIはアプリケーションを子プロセスとして起動する。

アプリケーションが終了すると：

```text
Other App exits
      │
      ▼
Default UI waits for UI
      │
      ▼
Reconnect
      │
      ▼
Show Main Screen
```

# 14. システム状態の取得

Default UIは、ロボット内部の状態を定期的に取得する。

## バッテリー

MCP3221をI2C経由で使用する。

```text
SDA = GPIO2
SCL = GPIO3
VDD = 3.3V
```

ADC値からバッテリー電圧を計算する。

```text
battery_voltage =
    raw_value / 4095 * 3.3 * 11
```

---

## CPU温度

以下を実行する。

```bash
vcgencmd measure_temp
```

例：

```text
temp=48.7'C
```

---

## CPU周波数

以下のファイルを読み取る。

```text
/sys/devices/system/cpu/cpufreq/policy0/cpuinfo_cur_freq
```

値はHzであるため、表示時にMHzへ変換する。

---

## Wi-Fi IP

Wi-FiインターフェースのIPv4アドレスを表示する。

通常は：

```text
wlan0
```

を対象とする。

---

# 15. バッテリー低電圧

バッテリー電圧が：

```text
6.5V未満
```

になった場合、低電圧状態とする。

Default UIは：

1. 画面に警告を表示
2. ブザーを鳴らす

低電圧状態が継続している間、ブザーを連続再生してはならない。

一定間隔で警告音を再生する。

Default UIから以下の操作が可能である。

# 18. AIエージェントへの重要な指示

AIエージェントは、個別の実装を開始する前に、以下を理解すること。

## 直接ハードウェアを操作しない

Default UIは以下を直接操作してはならない。

- OLED
- GPIOボタン
- PWMブザー

これらはすべて既存の `ui_server` が管理する。

Default UIは `ui_client.py` を利用する。

---

## PREEMPTEDを異常扱いしない

他のアプリケーションがUIを取得した場合、Default UIはUIを一時的に失う。

これは正常な動作である。

---

## Default UIはロボットのシェルである

Default UIは単なるステータス表示アプリではない。

ロボットの：

- ホーム画面
- アプリケーションランチャー
- システムモニター
- システム操作画面

を兼ねる。

---

## UIは小さく単純に保つ

96×64 OLEDと2つのボタンしかない。

機能を増やす場合も、UI操作を複雑にしない。

---

## エラー時もロボットを止めない

センサー、I2C、Socket、アプリケーションのいずれかに問題があっても、可能な限りDefault UI自体は動作を継続する。

取得できない値は：

```text
N/A
```

などで表示する。

---

# 19. 実装時の判断原則

実装上の詳細が未決定の場合、以下の原則で判断する。

1. 既存のui_serverとの互換性を最優先する。
2. ハードウェアへの直接アクセスを避ける。
3. UIをブロックしない。
4. 1つのクラスに過剰な責務を持たせない。
5. 将来のアプリケーション追加を容易にする。
6. 設定値は可能な限り設定ファイルまたは定数として分離する。
7. エラーはログへ記録する。
8. 失敗しても可能な限りサービスを継続する。
9. テスト可能なコードを書く。
10. 実装前に既存コードの実際のAPIと挙動を確認する。

---

# 20. 期待する開発の進め方

AIエージェントは、タスクを実装する際に以下の順序を推奨する。

1. 既存リポジトリを調査する
2. `ui_server`と`ui_client.py`の実際のAPIを確認する
3. 既存のプロジェクト構成を確認する
4. 必要な実装を小さな単位に分割する
5. テストを作成する
6. 実装する
7. テストを実行する
8. 既存機能との互換性を確認する
9. READMEを更新する
10. 変更内容を要約する

実装前に、既存コードの仕様を推測してはいけない。

実際のコードを確認し、既存のインターフェースに適合させること。

# 21. 最終的なシステム像

最終的には、ロボットを起動すると：

```text
Power On
    │
    ▼
systemd
    │
    ├── ui_server.service
    │
    └── default-ui.service
            │
            ▼
       Default UI
            │
            ▼
    Main Status Screen
```

ユーザーがLを押すと：

```text
Next Menu
```

Rを押すと：

```text
Select Menu
```

アプリケーションを選択すると：

```text
Default UI
    │
    ▼
Start Application
    │
    ▼
Application takes UI
    │
    ▼
Default UI is PREEMPTED
```

アプリケーションが終了すると：

```text
Application exits
    │
    ▼
Default UI reconnects
    │
    ▼
Default UI resumes
```

この循環が、ロボットの基本的なユーザーインターフェースライフサイクルである。
